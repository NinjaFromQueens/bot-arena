# Circuit Rebels — notes for Claude Code

Circuit Rebels (circuitrebels.org): free robotics lessons and class games for school robotics classes in NYC. Bot Arena is its classroom battle game. Teacher hosts on a projector; students join from Chromebooks/phones.

## Commands
- `npm install` then `npm start` (port 3000, or `PORT`)
- `npm run dev` restarts on file changes
- `npm test` runs bracket + battle determinism + bot codes, Flying Car Lab, music pattern, sensor lesson, motor lesson, robot arm lesson, balance, Brain Challenge, vacuum lesson, lesson files, glossary, Robot Racer, missions (every mission with every choice, its explanations and tips), the teacher's mission data against a real server (`missions-live.test.js`), problem sets (`sprint.test.js`), Speed Run against a real server (`sprint-live.test.js`), story files and step rules (`story.test.js`), the class Now signal (`now-live.test.js`), and art pack tests
- `npm run balance` prints win rates for every legal build. Run it after ANY change to `PARTS` or battle rules. Target: every part 45–55%, most builds 40–60%, ~11–14 attacks per fight.
- `node test/tune.js 250` hill-climbs the numbers in `PARTS` and prints a suggestion (does not edit files)
- `node test/tune-brain.js 120` does the same for the Custom brain's moves (power, aim, shield, counter) so good rules > default rules > no rules > bad rules

## Architecture
- No build step, no framework. Plain Node (Express + Socket.IO) and vanilla browser JS.
- `public/js/engine.js` is UMD and loaded by BOTH the server (`require`) and the browser (`window.Engine`). Keep it free of top-level browser-only calls; anything using `window`/`document` must stay inside functions.
- `Engine.simulate(a, b, seed)` must stay deterministic: only use the seeded `rnd()` inside it, never `Math.random()`. The server decides the winner from the seed and the host replays the same seed. If you change battle rules, both sides update together because they share this file.
- Server state is in memory (`rooms` Map). Restarting the server ends all games. That's acceptable for class use.
- Live lessons: the board's **Present a lesson** link opens `/learn?present` in the same tab; an inline script in learn.html makes that tab a host socket (page "host", so it isn't counted online) and learn.js's `present` resumes the game with the tab's `ba-host` sessionStorage. Every step goes to the server as `host:lesson` (lesson number, title, step, and the quiz with its answer when it's a quiz card). `room.lesson` is public without the answer until `host:reveal`; answers (`player:answer`, changeable until the reveal) are counted for the board only (`room:poll`). Reveal adds `qpts`. `host:lessonEnd` clears it. Host-sent text is trimmed and students render it with textContent.
- Flying Car Lab class challenge: the board's **Flying Car challenge** link opens `/lab?present` in the same tab (lab.html's inline script makes `window.baSocket`; `classLab` in lab.js resumes the game with `ba-host`). Picking a mission sends `host:lab` (a new mission clears the entries; `open` toggles submissions). Students submit from their own Lab page, which isn't the game page, so `player:labSubmit` and `lab:check` carry the saved `ba-session` pass and the server checks the token; `lab:check` also joins the socket to `lab:CODE` for `lab:info` updates. The server runs `Flight.clampDesign`, `simulate` and `grade` on every entry and sorts them (`labOrder`); the board gets entries with names via `room:lab` and replays them with `launch(result)`. Students' state has `lab: {m, n, open, ids}` only.
- Robot Racer: `public/js/race.js` (UMD) is the physics, the three `TRACKS` (built from `DEFS` by `makeTrack`: `SECTIONS` eased into 2 m `segs` with curvature `k` and `slope`, plus `steep`, `tight`, a `theme` and `keys` naming the straight, hill and corner the report talks about) and lap logic: fixed 1/60 s `step`, digital inputs encoded one letter per step (`encode`/`decode`), `lap(setup, inputs, track)` re-drives a whole lap (the server uses it to check submissions; the page uses it for the report and ghosts), `autopilot`/`autoLap` is a careful computer driver, `setupStats` the garage numbers, `explain` the lap report (its tips compare `autoTimes(track)` for every setup, so a suggested change is always faster; an unfinished lap counts as Infinity). Every function takes a track object or id (`trackOf`) and defaults to track 0. `climbSpeed(setup, slope)` is the steady climb speed (the HUD's hill profile colors climbs below 0.3 m/s red, below 3 yellow); `medals(track)`/`medalOf(time, track)`: gold = the track's `par` (the computer driver's best lap there, stored in `DEFS` so pages don't drive 36 laps; the race test fails with the new value if physics changes), silver +10%, bronze +25%, compared in hundredths like the display. Hills show in degrees (signs, garage; Operatives also see the percent grade). `Engine.gearPair(ctx, wx, wy, R, ratio, turn)` is the one gearbox picture (wheel gear fixed size, motor gear R/ratio with a small floor, turning `ratio` times as far), drawn in lesson 7's simulator, the garage (`drawGearPic`) and the HUD, where it turns with `car.z` at the real ratio. Car looks: `LOOK` (how many choices of body, c1, c2, liv, num, rim, trail, head) and `cleanLook` (bad values fall back to defaults); racedraw.js `LOOKS` has the names and colors (`PAINT` 12 colors, `TRAILS`, `BODIES`, `LIVERIES`, `RIMS`, `HEADS`: head 1-4 is a battle sensor + 1) and `kart(..., { look })` draws them (`SHAPE` per body); a kart without a look draws as before. Looks never touch physics. `test/race.test.js` checks determinism, that every lap ends at its start height, the trade-offs, each track's best gear for the computer driver (Garage Circuit 6:1, Desert Speedway 4:1, Neon Peaks 8:1 with 4:1 stalling), and the report's claims. Change any number in race.js and run it. `racedraw.js` (browser only, `window.RaceDraw`) draws: `world` (the road near-to-far with hill clipping, then seeded scenery and other karts far-to-near, with name tags and start lights), `kart`, `minimap`, `speedLines`; the race page and the Race Day board both use it. `racegame.js` is the race page: it records the lap from the same fixed steps. It also has the paint shop (`race-look` in localStorage; sent with `race:check {who, look}` and `race:look`), the rpm dial and hill profile in `hud`, the motor sound (`motorSound`, its own AudioContext, only with Sound on while racing), medals, and simple graphics (`race-low`, passed to `world` as `o.low`). Class laps: `race:submit` carries the `ba-session` pass and a `track`; the server re-drives the inputs and keeps each student's fastest per track (`room.race[track]`, a Map); `race:check` returns `boards` (one per track), `race:board` sends `{track, board}`, and `publicState.race` is the top 3 per track (with `track` and `n`) for the board.
- Race Day (a Grand Prix): the lobby's **Race Day** link opens `/raceday` in the same tab (`data-page="host"`; `raceday.js` resumes with `ba-host`). `room.gp = {tracks, i, phase, startAt, endAt, live, laps, setups, results}`; phases garage -> countdown (4 s, synced by `startAt`; clients use `gp.now - Date.now()` as the clock offset) -> racing -> results -> (next track's garage | done). Host events `host:gp {tracks}`, `host:gpGo`, `host:gpEndRace`, `host:gpNext`, `host:gpClose`. Students' race pages register with `race:check` (sets the socket's `raceMe`) and send `player:gpSetup` (garage only), `player:gpPos {z, x, v}` (clamped, at most ~8/s) and `player:gpLap {setup, inputs}` once per race (at most one try per second, since each one is driven again): the server re-drives it on the race's track, refuses one that finished faster than the time since the start, and ends the race early when every live racer is home (or after `GP_LIMIT` 150 s + 3). `gpTicker` sends `gp:live {t, cars: [[id, z, x, v, finished]]}` 5 times a second to `race:CODE` and the hosts; positions are for display only, results come from the re-driven laps. `gpState` (in `room:state` and `gp:state`) has `racers` (id, name, color, `look` from `p.raceLook`, checked by `Race.cleanLook`; `race:look` and `player:gpSetup` changes reach everyone at most every 300 ms via `gpSoon`), `setups`, `results` (per race, finishers by time then DNFs by distance, with `pts` from `GP_POINTS`), `standings` and, when done, `awards`. Pages draw rivals 200 ms behind live, interpolating between snapshots.
- Missions (the learning loop: predict, test, explain, improve): `public/js/missions.js` (UMD, no physics) reads mission files `public/data/missions/<id>.json` (order in `index.json`, ids never change) and asks each game's model, registered with `Missions.register(game, model)`, for everything else. A mission names its `game`, `lesson`, `setting`, the choices it `allow`s (everything else is fixed at `start`), a `predict` kind (`with: "choice"` or a fixed setup), a `goal` kind and tiered text (`tiers.recruit.brief`/`question` required; Cadet and Operative fall back to it). It never stores an answer: the model works it out, so a retune can't make a mission wrong. `Missions.choice` ignores anything outside `allow` (the server will use it on payloads). Racer: `Race.STRIPS` are point-to-point test benches built with `makeTrack` but kept out of `TRACKS` (so pickers, class boards and Race Day never list them; new strips go at the end); `Race.MISSION` has `setting`, `clamp`, `run(mission, setup, {inputs})` (the student's inputs re-driven, otherwise the computer driver), `predict.reachTop` and `goal.reachEnd`. Racer answers come from the computer driver's run on the strip, not `climbSpeed`, because a short hill never reaches steady speed. `test/missions.test.js` runs every mission with every allowed choice and fails if an answer is too close to a line (`close`), if no choice or every choice meets the goal, or if a known claim changes (gear-hill: 4:1 gets stuck, 6:1 and up make it). Mission screen: `/race?mission=<id>` (`mis` in racegame.js; nothing links to it until lesson 7 does): the brief, a garage with only the allowed choices and no answer hints before the prediction (no "stalls here", stats bars or red hill colors), `Cards.predict` (Run waits for a pick; it locks on Run), a run that ends 2 s after the car stops, then the verdict, the one-change line and `Cards.explain` from `Race.MISSION.explain` (findings, a speed graph from `Race.trace`, glossary tooltips, one tip whose "Try it" change the test proves is better). Progress stays on the device in `cr-missions`; mission runs never touch `race-setup` or `race-bests`, and class games and Race Day are off on a mission page. `public/js/cards.js` (browser, `window.Cards`) holds the predict and explain cards for every game (`Cards.predict` takes `go`, the run button's name, and `kicker`); their styles (`.pcard`, `.verdict`, `.changeline`) are in style.css. Strips with `open: true` draw flat past both ends (`segIdx` in racedraw.js); looped tracks draw exactly as before. Lesson 7 (`dcmotor`) ends with `next: { mission: "gear-hill" }` and lists `gear-hill`, `gear-straight` (`topGear`: 4:1 has the highest top speed) and `hill-straight` (`firstHome`: 6:1 wins the hill-then-straight trade-off); learn.js turns `next.mission` into `/race?mission=…` or `/lab?mission=…` by `next.game` (`racer`, `lab`; the lesson test checks it matches the mission's game), and the tests check lessons and missions link both ways. Kinds with `once: true` (`Missions.once`: the "which gear wins?" questions) are asked before the first run only; the page keeps a "Your tests so far" table and reveals the verdict and the winner only after every allowed choice has been tried (no confetti before that). Goal `bestGear` = finished with the computer driver's fastest allowed gear (`met(mission, r, choice)`). After a goal, the page offers the lesson's next mission in `index.json` order. The offline copies carry `MISSION_DATA`, `GLOSSARY_DATA` and `OFFLINE_PAGES` (the lesson button opens `robot-racer-offline.html?mission=…`). Reading levels on missions: a switch in the mission panel (Cadet / Recruit / Operative, `Tier.set` saves `cr-tier` on the device) picks the brief, the question and `tiers[t].drive`: `auto` = "Torque drives" (`stepInput` applies `Race.autopilot` inside the fixed steps, so a Cadet's run equals the computer driver's), `assist` = steering help (on by default, a checkbox switches it off; the autopilot steers, the keys work gas and brake), `full` = full control. `lastIn` is the input the last step really used (kart drawing, the stall warning). After a mission run or a free-play lap (not Race Day), `showResultCard` puts the result on the track view (`#rescard`: made it or stuck, the prediction, See why, Next try or Race again) and the HUD skips its big banner.
- Part art: `drawBot` draws a body, sensor head or tool from a picture when an art pack has one loaded (`artPart`; frames: body from the ground under the robot, sensor from the head's middle, tool from the hand along the arm), and from code otherwise. Tool pictures get the same motion as the coded tools (hammer `o.hammer`, spinner around `pivot`, flipper `o.flipA`, gripper squeeze). `tint` colors a gray template with the robot's color. `Engine.loadArt(url, extra)` builds the pack (host, play and practice call it with `/art/manifest.json`; the server answers an empty pack when `public/art/` doesn't exist). Practice mode adds students' own uploads (`rba-art` in localStorage, never sent anywhere). The format is documented in `public/art-sample/README.md`, and `test/art.test.js` checks the sample pack (and `public/art/` if present). Keep `TORSO_Y` in step with the torso heights of the coded bodies.

- Teacher status page: `public/status.html` + `GET /api/status` (header `x-teacher-pin` must match the `TEACHER_PIN` env var; 503 when it isn't set, 401 wrong, 429 after 10 wrong tries per IP in 10 min; `trust proxy` is on so Render's proxy doesn't count as one IP). Counts and room codes only, never names. `RENDER_GIT_COMMIT` is the deployed version.
- Home page (Circuit Rebels): `public/index.html` + `public/css/home.css`, loaded after style.css and scoped to `.hp` on `<body>` (`.hp-html` on `<html>`), so the games and offline backups don't change. Pictures are in `public/img/home/` (WebP; `share.jpg` is the link-preview picture). The join form keeps its ids (`#joinform`, `#code`, `#msg`) and `room:check` flow; "Join a game" links point to `#joinform` and focus the code box; `#online` is filled by presence.js. Navbar links go to `/tour`, `/learn` and sections of this page (`#games`, `#schools`, `#about`) until those pages exist. Sections with `.hp-reveal` fade in on scroll only when motion is allowed and JS has added `hp-js`; in grids that hold the code box use `minmax(0, 1fr)` so it can't push the card past a phone's width. The questions in the page's `application/ld+json` block must match the visible Questions and answers word for word. Public pages show only spoiler-free story art (the crew, the hooded Dr. Lazarus). `public/robots.txt` and `public/sitemap.xml` list circuitrebels.org as the main address; add new public pages to the sitemap.
- All battle numbers live in `Engine.PARTS` (plus `Engine.TUNE`). Mechanics: dodge, burst (bonus attack), heavy (can't be grabbed), acc, swings, mult, grab, Defensive shield/counter, Smart wait-for-aim, low (Wedge: can't be flipped), glance (Wedge: spinner damage kept), track (Lidar: share of dodge ignored), spin (Spinner), flip (Flipper: target loses a turn, works on Treads), pierce (Drill: share of armor ignored). New parts go at the END of their slot so old bot codes keep working. `npm test` runs `test/balance.test.js`: every part 45–55%, 10–15 attacks per fight, 70%+ of builds within 40–60%, plus the counter claims the tips make. After changing numbers, `node test/tune.js 300` (update its `KNOBS`/`ORDER` for new parts) and recheck tip text against the claims list. Part `tip` text is shown to students and must stay true; check it against `npm run balance` matchups.
- Custom brain (`PARTS.brain[3]`, `custom: true`): students' if-then rules live in `bot.rules` (`[{c, v, a}]`, max 3). The vocabulary is `Engine.RULES` (IF conditions with number choices, DO moves); `chooseRule` picks the first true rule at the start of each turn, before the attack. Moves: power attack (`powerDmg`/`powerAcc`; smashes a shield: full damage, no counter), aim first (skip; the next attack gets `aimAcc`/`aimDmg`; no bonus speed attack that turn), shield (skip; brace; the next turn is always the counterattack with `counter`). Think events carry `act` and `rule`, act events carry `smash`. Codes are `NAME-bsbtc-RRR…` (`codeOf`/`parseCode`), checked by `sanitizeBot`; never reorder `RULES.IF` or `RULES.DO` because codes store positions. The balance test gives Custom builds `RULES.defaults` and also checks rule claims (good > defaults > none, aim below 40% beats below 80%, power beats shield). Retune move numbers with `tune-brain.js`, not `tune.js`. The editor is `renderRules` in builder.js; `explainBattle` has a `rules` reason and a `ruleTip` for losing Custom brains.
- Socket events: `host:create|resume|start|next|lock|matchDone|kick|reset|reactions|settings|lesson|reveal|lessonEnd|lab|labEnd|gp|gpGo|gpEndRace|gpNext|gpClose|now|live|mute|chatClear|announce|watch|watchCtl`, `player:join|update|leave|predict|react|answer|labSubmit|gpSetup|gpPos|gpLap|chat|mission|sprintAnswer|sprintMe`, `host:sprint|sprintNext|sprintReveal|sprintEnd`, `room:check`, `lab:check`, `race:check|submit|ghost` (server sends `race:board`, `gp:state`, `gp:live`, `room:chat|chatlog|chatClear|watch|watchCtl`). Server broadcasts `room:state` and `room:result` (with `correct` predictor ids). Board-only events go through `toHosts(room, ...)` to `room.hosts` (the host's socket ids): `room:react`, `room:status`, `room:poll`, `room:lab`, `room:missions`, `room:sprintStats`.
- Teacher's mission data (R-19, shared-parts-spec section 9): in a class game, `Missions.send(m, p, c, run)` (browser only; the Racer sends `{inputs}`) emits `player:mission {who, m, p, c, run}` after each mission run from the Racer, Lab and Brain Challenge pages (practice.html now sets `window.baSocket`). Solo play sends nothing. The server (`MISSION_FILES`, read once at start) checks the pass (`labPlayer`), the mission and the prediction, allows one a second (`wait: true`, and the page sends again up to 3 times), clamps `c` with `Missions.choice`, works out `correct`, the goal (re-driving Racer inputs) and the change count (`Missions.changes`; a model can count its own way: a Brain Challenge rule added, removed or edited is one change), and keeps `room.missions` (player id -> mission id -> `{first, tries, one, several, goal, last}`; `first` = the first try's prediction). `missionData` sends `{rows: [pid, mid, first, tries, one, several, goal], summary: [mid, title, students, firstRight, goalMet, oneAtATime]}` to the board only, leaving out students no longer in the game; kick drops a student's rows, `host:reset` clears it, `host:resume` catches a board up. The board's Class missions panel (`#misp` in the lobby, `#misp2` beside the bracket, `renderMissions` in host.js) shows the totals; the per-student table appears only with "Show names", which is off on every load. A reply with `gone: true` (no such game) drops the class's reading level on the device.
- Presence: `public/js/presence.js` runs on every page (`<body data-page="...">`), reusing the page's socket via `window.baSocket` where it has one, and loading before the page script on lessons/Lab/practice so the first lesson or mission gets reported. It sends `presence:hello {page, n, who, watch}` and `presence:where {n}`: numbers only, never text. `who` is the saved `ba-session` game pass; the server links a device to a student only if the token matches. The home page gets anonymous `presence:counts` (hosts aren't counted), and hosts get `room:status` (playerId -> page + number) through `toHosts`. Pages disconnect on `pagehide` so Back-button caches don't count as online. The offline build strips the Socket.IO tag, so presence does nothing there.
- Class chat: `Engine.QUICK` is the only chat text; `player:chat {q}` sends a position (`{a}`/`{b}` are filled in by the server from `room.current` and refused without a match). One message per student per 3 s (10 s with `slow`). `room.live = {chat, slow, fights}` (`host:live`), `room.muted` (`host:mute`), both in `publicState.live` (with `muted` as ids). `room.chatLog` keeps the last 40 in memory and goes to a (re)joining player and a resuming host as `room:chatlog`; `host:chatClear` sends `room:chatClear`. Messages broadcast as `room:chat {id, pid, name, text, side, t}`. `host:announce {text}` (140 chars, whitespace tidied) sets `room.announce {text, t}` in state; devices show it for 10 minutes as text. The board's `#chatp` panel moves between `#chatslot-lobby` and `#chatslot-tour` (`.slot` is `display: contents`) and only rebuilds its list when the messages, mutes or chat setting change; bubbles go in `#chatlayer` on the cheered robot's side. `test/live.test.js` covers chat, watching and Race Day positions.
- Fights on students' devices: after `host:lock`, host.js's `playGame` emits `host:watch {matchId, g, speed}` as the board's fight starts; the server checks the match is current and predictions are closed, sets `room.watching`, and sends `room:watch {matchId, g, seed, a, b, round, bestOf, speed}` (nothing when `fights` is off). play.js replays it with its own BattleStage on `#w-arena` (shown before `play`, because a stage only advances while it's on screen) and closes it when `currentMatchId` moves on. `host:watchCtl {speed|skip}` (from the speed buttons and Skip while a real match plays) becomes `room:watchCtl`; replays never emit. `gp:live` goes to the whole room (boards and students' game pages, where play.js draws a leader-cam view and the top 5 in the Race Day card) as well as `race:CODE`.
- Reactions: students send an index into `Engine.REACTIONS` (anonymous, never a name), one per student per 1.2 s, ignored in the lobby or when the host switches them off (`room.reactionsOff`, sent to devices as `state.reactions`).
- `Engine.explainBattle(a, b, sim)` turns a fight's events into reasons + a loser-aware tip (`sides[k]`). Used by the host board, practice, and the server (sent to fighters in `room:result.why`). If you add a battle mechanic, add its event flag in `simulate` and a reason/tip here.
- Match flow: `host:next` opens predictions and returns the seeds -> host shows the Up Next card -> `host:lock` closes predictions -> host plays the seeded fight(s) -> `host:matchDone` awards prediction points, records stats, and computes awards when the final ends.
- Room settings (`room.settings`, changed with `host:settings` from the lobby): `maxw` is the weight class (`Engine.WEIGHT_CLASSES`: 50/75/100, lobby only) and `bo3` (0 off, 1 final, 2 semifinals + final), and `tier` ("" = students choose, or cadet/recruit/operative; any time). The game page saves the class's level as `cr-class-tier {code, tier}` (`Tier.setClass`), and `Tier.current()` uses it while the device's `ba-session` is for that game (`Tier.classTier()`); the Racer's reading-level chips lock with a tip. Best of 3: `host:next` picks every game's seed up front and the server's `winnerId` is whoever wins 2; the match carries `seeds` and `bestOf`, and `host.js` plays them one by one (`series`, `playGame`). Robots are validated against the heaviest class on join (so a rejoin never fails), then the room's limit: new joins and updates over it are refused, existing ones get `over: true`, and `host:start` refuses while any are over. `explainBattle(a, b, sim, maxw)` swaps out any tip naming a part that can't fit (`partsTooHeavy`); pass the room's limit. Balance is tuned and tested at 75 kg only. `room:check` also returns `maxw` so the build screen knows the limit before joining.
- `public/practice.html` + `public/js/practice.js` use the same engine/builder/battle code. Tabs: Build, Arena, Challenges (`#build|#arena|#challenges`). Both stages share `hud(prefix)` and `showWhy(…, prefix)` (ids `ch-…` for the Challenges stage).
- Brain Challenges: `public/js/challenges.js` (UMD) holds the five challenges: the student's fixed robot (`you`, Custom brain), the `boss`, a `seed` (fights use seed..seed+9), `hints`, `lesson`, plus `answer` and `naive` rule codes for the test. `test/challenges.test.js` checks each answer wins 6+/10, every naive set loses, no single rule beats MEGA, and the numbers the intro text claims. ANY change to battle numbers can break a challenge: run `npm test`, and if one fails, re-pick its seed (search seeds where the answer wins 7+ and naive sets 4 or fewer) or its robots. The rules editor is shared: `Builder.rulesEditor(box, rules, onChange)`. Progress lives in localStorage (`rba-challenges`, `rba-ch-rules`). ## Conventions
- Validate every client payload on the server (`Engine.sanitizeBot`, `cleanBuilder`, name filter).
- Student-facing copy: short, plain sentences, encouraging tone. Kids are roughly grades 5–10.
- Tooltips: every control gets `data-tip="..."` (handled by `public/js/tips.js`, loaded on every page; it works on hover, keyboard focus and touch). Give new buttons and settings a tip, and keep tip text true to the code, like part tips. Controls built in JS set it where they're created (`builder.js`, `lab.js`, `learn.js`, `practice.js`, `host.js`).
- Host keyboard: Space / → / PageDown run Next match (for presentation clickers), ignored while focus is in a form control or button.
- Visual style: dark "garage" theme, orange `#f46524` accent, Chakra Petch / Barlow Semi Condensed / JetBrains Mono. Tokens live in `public/css/style.css`.
- Respect `prefers-reduced-motion` (Engine.RM) for shakes and particles.
- Sound and Music are off by default; their buttons turn them on. Music only plays on the host board, never on students' devices.
