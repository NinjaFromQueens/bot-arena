# Bot Arena — notes for Claude Code

Classroom robotics battle game for a middle/high school robotics class (Fall Robotics Academy, NYC). Teacher hosts on a projector; students join from Chromebooks/phones.

## Commands
- `npm install` then `npm start` (port 3000, or `PORT`)
- `npm run dev` restarts on file changes
- `npm test` runs bracket + battle determinism + bot codes, Flying Car Lab, music pattern, sensor lesson, motor lesson, robot arm lesson, balance, Brain Challenge, vacuum lesson, Robot Racer, and art pack tests
- `npm run balance` prints win rates for every legal build. Run it after ANY change to `PARTS` or battle rules. Target: every part 45–55%, most builds 40–60%, ~11–14 attacks per fight.
- `node test/tune.js 250` hill-climbs the numbers in `PARTS` and prints a suggestion (does not edit files)
- `node test/tune-brain.js 120` does the same for the Custom brain's moves (power, aim, shield, counter) so good rules > default rules > no rules > bad rules

## Architecture
- No build step, no framework. Plain Node (Express + Socket.IO) and vanilla browser JS.
- `public/js/engine.js` is UMD and loaded by BOTH the server (`require`) and the browser (`window.Engine`). Keep it free of top-level browser-only calls; anything using `window`/`document` must stay inside functions.
- `Engine.simulate(a, b, seed)` must stay deterministic: only use the seeded `rnd()` inside it, never `Math.random()`. The server decides the winner from the seed and the host replays the same seed. If you change battle rules, both sides update together because they share this file.
- Server state is in memory (`rooms` Map). Restarting the server ends all games. That's acceptable for class use.
- Live lessons: the board's **Present a lesson** link opens `/learn?present` in the same tab; an inline script in learn.html makes that tab a host socket (page "host", so it isn't counted online) and learn.js's `present` resumes the game with the tab's `ba-host` sessionStorage. Every step goes to the server as `host:lesson` (lesson number, title, step, and the quiz with its answer when it's a quiz card). `room.lesson` is public without the answer until `host:reveal`; answers (`player:answer`, changeable until the reveal) are counted for the board only (`room:poll`). Reveal adds `qpts`. `host:lessonEnd` clears it. Host-sent text is trimmed and students render it with textContent.
- Flying Car Lab class challenge: the board's **Flying Car challenge** link opens `/lab?present` in the same tab (lab.html's inline script makes `window.baSocket`; `classLab` in lab.js resumes the game with `ba-host`). Picking a mission sends `host:lab` (a new mission clears the entries; `open` toggles submissions). Students submit from their own Lab page, which isn't the game page, so `player:labSubmit` and `lab:check` carry the saved `ba-session` pass and the server checks the token; `lab:check` also joins the socket to `lab:CODE` for `lab:info` updates. The server runs `Flight.clampDesign`, `simulate` and `grade` on every entry and sorts them (`labOrder`); the board gets entries with names via `room:lab` and replays them with `launch(result)`. Students' state has `lab: {m, n, open, ids}` only.
- Robot Racer: `public/js/race.js` (UMD) is the physics, the three `TRACKS` (built from `DEFS` by `makeTrack`: `SECTIONS` eased into 2 m `segs` with curvature `k` and `slope`, plus `steep`, `tight`, a `theme` and `keys` naming the straight, hill and corner the report talks about) and lap logic: fixed 1/60 s `step`, digital inputs encoded one letter per step (`encode`/`decode`), `lap(setup, inputs, track)` re-drives a whole lap (the server uses it to check submissions; the page uses it for the report and ghosts), `autopilot`/`autoLap` is a careful computer driver, `setupStats` the garage numbers, `explain` the lap report (its tips compare `autoTimes(track)` for every setup, so a suggested change is always faster; an unfinished lap counts as Infinity). Every function takes a track object or id (`trackOf`) and defaults to track 0. `climbSpeed(setup, slope)` is the steady climb speed (the HUD's hill profile colors climbs below 0.3 m/s red, below 3 yellow); `medals(track)`/`medalOf(time, track)`: gold = the computer driver's best lap on that track rounded to hundredths, silver +10%, bronze +25%, compared in hundredths like the display. Car looks: `LOOK` (how many choices of body, c1, c2, liv, num, rim, trail, head) and `cleanLook` (bad values fall back to defaults); racedraw.js `LOOKS` has the names and colors (`PAINT` 12 colors, `TRAILS`, `BODIES`, `LIVERIES`, `RIMS`, `HEADS`: head 1-4 is a battle sensor + 1) and `kart(..., { look })` draws them (`SHAPE` per body); a kart without a look draws as before. Looks never touch physics. `test/race.test.js` checks determinism, that every lap ends at its start height, the trade-offs, each track's best gear for the computer driver (Garage Circuit 6:1, Desert Speedway 4:1, Neon Peaks 8:1 with 4:1 stalling), and the report's claims. Change any number in race.js and run it. `racedraw.js` (browser only, `window.RaceDraw`) draws: `world` (the road near-to-far with hill clipping, then seeded scenery and other karts far-to-near, with name tags and start lights), `kart`, `minimap`, `speedLines`; the race page and the Race Day board both use it. `racegame.js` is the race page: it records the lap from the same fixed steps. It also has the paint shop (`race-look` in localStorage; sent with `race:check {who, look}` and `race:look`), the rpm dial and hill profile in `hud`, the motor sound (`motorSound`, its own AudioContext, only with Sound on while racing), medals, and simple graphics (`race-low`, passed to `world` as `o.low`). Class laps: `race:submit` carries the `ba-session` pass and a `track`; the server re-drives the inputs and keeps each student's fastest per track (`room.race[track]`, a Map); `race:check` returns `boards` (one per track), `race:board` sends `{track, board}`, and `publicState.race` is the top 3 per track (with `track` and `n`) for the board.
- Race Day (a Grand Prix): the lobby's **Race Day** link opens `/raceday` in the same tab (`data-page="host"`; `raceday.js` resumes with `ba-host`). `room.gp = {tracks, i, phase, startAt, endAt, live, laps, setups, results}`; phases garage -> countdown (4 s, synced by `startAt`; clients use `gp.now - Date.now()` as the clock offset) -> racing -> results -> (next track's garage | done). Host events `host:gp {tracks}`, `host:gpGo`, `host:gpEndRace`, `host:gpNext`, `host:gpClose`. Students' race pages register with `race:check` (sets the socket's `raceMe`) and send `player:gpSetup` (garage only), `player:gpPos {z, x, v}` (clamped, at most ~8/s) and `player:gpLap {setup, inputs}` once per race: the server re-drives it on the race's track, refuses one that finished faster than the time since the start, and ends the race early when every live racer is home (or after `GP_LIMIT` 150 s + 3). `gpTicker` sends `gp:live {t, cars: [[id, z, x, v, finished]]}` 5 times a second to `race:CODE` and the hosts; positions are for display only, results come from the re-driven laps. `gpState` (in `room:state` and `gp:state`) has `racers` (id, name, color, `look` from `p.raceLook`, checked by `Race.cleanLook`; `race:look` changes reach Race Day at most every 300 ms via `gpLooks`), `setups`, `results` (per race, finishers by time then DNFs by distance, with `pts` from `GP_POINTS`), `standings` and, when done, `awards`. Pages draw rivals 200 ms behind live, interpolating between snapshots.
- Part art: `drawBot` draws a body, sensor head or tool from a picture when an art pack has one loaded (`artPart`; frames: body from the ground under the robot, sensor from the head's middle, tool from the hand along the arm), and from code otherwise. Tool pictures get the same motion as the coded tools (hammer `o.hammer`, spinner around `pivot`, flipper `o.flipA`, gripper squeeze). `tint` colors a gray template with the robot's color. `Engine.loadArt(url, extra)` builds the pack (host, play and practice call it with `/art/manifest.json`; the server answers an empty pack when `public/art/` doesn't exist). Practice mode adds students' own uploads (`rba-art` in localStorage, never sent anywhere). The format is documented in `public/art-sample/README.md`, and `test/art.test.js` checks the sample pack (and `public/art/` if present). Keep `TORSO_Y` in step with the torso heights of the coded bodies.
- Teacher status page: `public/status.html` + `GET /api/status` (header `x-teacher-pin` must match the `TEACHER_PIN` env var; 503 when it isn't set, 401 wrong, 429 after 10 wrong tries per IP in 10 min; `trust proxy` is on so Render's proxy doesn't count as one IP). Counts and room codes only, never names. `RENDER_GIT_COMMIT` is the deployed version.
- All battle numbers live in `Engine.PARTS` (plus `Engine.TUNE`). Mechanics: dodge, burst (bonus attack), heavy (can't be grabbed), acc, swings, mult, grab, Defensive shield/counter, Smart wait-for-aim, low (Wedge: can't be flipped), glance (Wedge: spinner damage kept), track (Lidar: share of dodge ignored), spin (Spinner), flip (Flipper: target loses a turn, works on Treads), pierce (Drill: share of armor ignored). New parts go at the END of their slot so old bot codes keep working. `npm test` runs `test/balance.test.js`: every part 45–55%, 10–15 attacks per fight, 70%+ of builds within 40–60%, plus the counter claims the tips make. After changing numbers, `node test/tune.js 300` (update its `KNOBS`/`ORDER` for new parts) and recheck tip text against the claims list. Part `tip` text is shown to students and must stay true; check it against `npm run balance` matchups.
- Custom brain (`PARTS.brain[3]`, `custom: true`): students' if-then rules live in `bot.rules` (`[{c, v, a}]`, max 3). The vocabulary is `Engine.RULES` (IF conditions with number choices, DO moves); `chooseRule` picks the first true rule at the start of each turn, before the attack. Moves: power attack (`powerDmg`/`powerAcc`; smashes a shield: full damage, no counter), aim first (skip; the next attack gets `aimAcc`/`aimDmg`; no bonus speed attack that turn), shield (skip; brace; the next turn is always the counterattack with `counter`). Think events carry `act` and `rule`, act events carry `smash`. Codes are `NAME-bsbtc-RRR…` (`codeOf`/`parseCode`), checked by `sanitizeBot`; never reorder `RULES.IF` or `RULES.DO` because codes store positions. The balance test gives Custom builds `RULES.defaults` and also checks rule claims (good > defaults > none, aim below 40% beats below 80%, power beats shield). Retune move numbers with `tune-brain.js`, not `tune.js`. The editor is `renderRules` in builder.js; `explainBattle` has a `rules` reason and a `ruleTip` for losing Custom brains.
- Socket events: `host:create|resume|start|next|lock|matchDone|kick|reset|reactions|settings|lesson|reveal|lessonEnd|lab|labEnd|gp|gpGo|gpEndRace|gpNext|gpClose`, `player:join|update|leave|predict|react|answer|labSubmit|gpSetup|gpPos|gpLap`, `room:check`, `lab:check`, `race:check|submit|ghost` (server sends `race:board`, `gp:state`, `gp:live`). Server broadcasts `room:state` and `room:result` (with `correct` predictor ids). Board-only events go through `toHosts(room, ...)` to `room.hosts` (the host's socket ids): `room:react`, `room:status`, `room:poll`, `room:lab`.
- Presence: `public/js/presence.js` runs on every page (`<body data-page="...">`), reusing the page's socket via `window.baSocket` where it has one, and loading before the page script on lessons/Lab/practice so the first lesson or mission gets reported. It sends `presence:hello {page, n, who, watch}` and `presence:where {n}`: numbers only, never text. `who` is the saved `ba-session` game pass; the server links a device to a student only if the token matches. The home page gets anonymous `presence:counts` (hosts aren't counted), and hosts get `room:status` (playerId -> page + number) through `toHosts`. Pages disconnect on `pagehide` so Back-button caches don't count as online. The offline build strips the Socket.IO tag, so presence does nothing there.
- Reactions: students send an index into `Engine.REACTIONS` (anonymous, never a name), one per student per 1.2 s, ignored in the lobby or when the host switches them off (`room.reactionsOff`, sent to devices as `state.reactions`).
- `Engine.explainBattle(a, b, sim)` turns a fight's events into reasons + a loser-aware tip (`sides[k]`). Used by the host board, practice, and the server (sent to fighters in `room:result.why`). If you add a battle mechanic, add its event flag in `simulate` and a reason/tip here.
- Match flow: `host:next` opens predictions and returns the seeds -> host shows the Up Next card -> `host:lock` closes predictions -> host plays the seeded fight(s) -> `host:matchDone` awards prediction points, records stats, and computes awards when the final ends.
- Room settings (`room.settings`, changed with `host:settings` from the lobby): `maxw` is the weight class (`Engine.WEIGHT_CLASSES`: 50/75/100, lobby only) and `bo3` (0 off, 1 final, 2 semifinals + final). Best of 3: `host:next` picks every game's seed up front and the server's `winnerId` is whoever wins 2; the match carries `seeds` and `bestOf`, and `host.js` plays them one by one (`series`, `playGame`). Robots are validated against the heaviest class on join (so a rejoin never fails), then the room's limit: new joins and updates over it are refused, existing ones get `over: true`, and `host:start` refuses while any are over. `explainBattle(a, b, sim, maxw)` swaps out any tip naming a part that can't fit (`partsTooHeavy`); pass the room's limit. Balance is tuned and tested at 75 kg only. `room:check` also returns `maxw` so the build screen knows the limit before joining.
- `public/practice.html` + `public/js/practice.js` use the same engine/builder/battle code. Tabs: Build, Arena, Challenges (`#build|#arena|#challenges`). Both stages share `hud(prefix)` and `showWhy(…, prefix)` (ids `ch-…` for the Challenges stage).
- Brain Challenges: `public/js/challenges.js` (UMD) holds the five challenges: the student's fixed robot (`you`, Custom brain), the `boss`, a `seed` (fights use seed..seed+9), `hints`, `lesson`, plus `answer` and `naive` rule codes for the test. `test/challenges.test.js` checks each answer wins 6+/10, every naive set loses, no single rule beats MEGA, and the numbers the intro text claims. ANY change to battle numbers can break a challenge: run `npm test`, and if one fails, re-pick its seed (search seeds where the answer wins 7+ and naive sets 4 or fewer) or its robots. The rules editor is shared: `Builder.rulesEditor(box, rules, onChange)`. Progress lives in localStorage (`rba-challenges`, `rba-ch-rules`).
- Replays: `host:matchDone` stores the match's `seeds` on its bracket match and `publicState` sends them; the board's ▶ (`startReplay`/`replayGame` in host.js) replays them with `E.simulate` and never emits anything. `replay` blocks Next match and Auto-play while it runs; its `onDone` branch returns before the match flow. The champion ceremony gets `podiumOf(bracket)` (final loser, semifinal losers) via `stage.showChampion(bot, label, podium)`.
- `public/js/battle.js` (BattleStage) is presentation only: it animates the events `simulate` already decided. Each tool connects at its own moment (`HIT`: gripper 0.2 s, hammer 0.34 s after its wind-up, spinner 0.22 s), with `reachAt`/`hammerAt` for the choreography. Impacts add hit-stop (`freeze`), and crits add a soft flash, a camera punch and a crowd cheer; KOs add slow motion. `drawBot` takes `reach`, `hammer`, `clamp`, `spinA`, `damage` (scars, cracked visor) and `pose: "win"`. The still parts of the garage arena are cached per canvas size in `backdrop()`. Keep shake, flash, zoom, afterimages and camera flashes behind `!RM`. Sense moments draw per sensor (`this.bots[e.me].sensor`: camera brackets, ultrasonic waves, touch whiskers, lidar sweep with dots) and show the hit chance parsed from the event text; robots under 35 HP smoke; a banner matching `/\bFINAL\b/` gets gold spotlights.
- Flying Car Lab: `public/js/flight.js` (UMD, deterministic physics + missions + `grade` + `explain`) and `public/lab.html` / `public/js/lab.js` (UI + canvas). Single-device only; progress and design live in localStorage. After changing any number in flight.js run `npm test` (lab.test.js has a saved solution per mission) and `npm run lab` to see how hard each mission is. Explanations must stay true to the sim: if you add a mechanic, add a finding and a tip for it in `explain`/`tipFor`.

- If-then rules lesson ("Think: if-then rules", lesson 6 in `learn.js`): its robot vacuum uses `public/js/rulebot.js` (UMD): a grid room, rules checked top to bottom each turn (first true wins, none = wait), and a run stops when a state repeats (it would loop forever). `test/rulebot.test.js` checks the experiments' claims (the starting rule bumps, a rule under IF always never runs, wall-only falls down the stairs, the full program cleans the room).
- Sensor lessons (Ultrasonic, Lidar, Sensor showdown in `learn.js`): their simulators use `public/js/sensors.js` (UMD). `Sensors.read` decides what each sensor detects and writes the student-facing reason; `Sensors.cast` is the lidar ray caster. Lesson text and quizzes rely on these rules (ultrasonic: soft, tilted, past 4 m; lidar: glass; infrared: glass, black, past 0.8 m), and `test/sensors.test.js` checks them. Change a rule and the tests tell you which lesson claim broke.
- Motor lessons (DC motors and gears, Servo motors, Stepper motors, Pick the right motor in `learn.js`): their simulators use `public/js/motors.js` (UMD). `drive(gear, rampDeg, volts)` is the DC motor + gearbox model (linear torque-speed line, 80% gearbox efficiency), `servoAngle`/`servoStep` the servo (1.0–2.0 ms → 0–180°, feedback loop), `stepperRun` the stepper (200 steps/turn, steps slip past `maxRate` for the load). `test/motors.test.js` checks every claim the lessons and quizzes make (stalls, fastest gear, pulse widths, skipped steps). Volts stay at 3 V and 6 V: small hobby motors are made for about that, and 9 V gave silly speeds.
- Robot arm lessons (Links and joints, Arm strength in `learn.js`): `public/js/arm.js` (UMD). `forward`/`inverse` are 2-link kinematics (18 + 14 cm, shoulder 0–180°, elbow ±150°; "elbow up" means the solution with the higher elbow, worked out geometrically, not by sign). `BLOCKS` are the targets (green and blue reachable, red out of reach on purpose). `holdTorque(kg, cm, angle)` is (block + half the 40 g link) × sideways distance, in kg·cm. `test/arm.test.js` checks the lesson claims (32 cm reach, two solutions for blue, small servo fails at 70° and holds at 75°). In `learn.js` use `E.ease`, not a bare `ease`: it isn't imported there.
- Host-board music: `public/js/music.js` (UMD, browser-only synth, no audio files): original chiptune tracks on an NES-style chip (`makeChip`: pulse waves at duty 0.125/0.25/0.5, a triangle, 15-bit shift-register noise). Tracks are pattern strings in `TRACKS` (one chord per bar, 16 steps per bar; token key and instruments at the top of the file: `pulse` with `duty`/`vib`/`echo`/`gate`, `tri`, `arp`, `drums` kshoxt). `host.js` calls `Music.play(scene)`: `garage` in the lobby and between matches, `hype` on the Up Next card, `null` (silence) for the countdown and at each KO, `fight` from the first move, `champion` 1.5 s after the fanfare. `VOL` keeps it under the sound effects. Sound effects (`Engine.Sound` in engine.js) use the same chip and are scheduled from "now" without timers, so `Sound.render(name)` and `Music.render(name, seconds)` can render offline (used by `/soundtest`-style previews and level checks). `test/music.test.js` checks every pattern is well-formed, fits the chord loop and stays in range, and that every `Sound.play("name")` in the pages exists in `Sound.names`. Keep the tunes original (no melodies from real games).

- `offline/*.html` are generated single-file backups (practice, Lab, lessons, Robot Racer). Run `npm run offline` after changing anything in `public/` so they stay in sync; never edit them by hand.

## Conventions
- Validate every client payload on the server (`Engine.sanitizeBot`, `cleanBuilder`, name filter).
- Student-facing copy: short, plain sentences, encouraging tone. Kids are roughly grades 5–10.
- Tooltips: every control gets `data-tip="..."` (handled by `public/js/tips.js`, loaded on every page; it works on hover, keyboard focus and touch). Give new buttons and settings a tip, and keep tip text true to the code, like part tips. Controls built in JS set it where they're created (`builder.js`, `lab.js`, `learn.js`, `practice.js`, `host.js`).
- Host keyboard: Space / → / PageDown run Next match (for presentation clickers), ignored while focus is in a form control or button.
- Visual style: dark "garage" theme, orange `#f46524` accent, Chakra Petch / Barlow Semi Condensed / JetBrains Mono. Tokens live in `public/css/style.css`.
- Respect `prefers-reduced-motion` (Engine.RM) for shakes and particles.
- Sound and Music are off by default; their buttons turn them on. Music only plays on the host board, never on students' devices.
